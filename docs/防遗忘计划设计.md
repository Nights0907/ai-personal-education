# 防遗忘计划（随访计划模式）设计

版本：v1.0（待评审）
日期：2026-11-03
前置：`docs/学生档案消费.md`（RecallPlan 决策引擎）、`docs/学生档案遗忘维度设计.md`（HLR 遗忘模型）。

## 1. 目标与定位

把"到点被动提醒"升级为"**主动的随访式防遗忘计划**"，类比 AI 医生随访计划（care plan）：不是一次性把题发给学生，而是**持续检测哪些题目已到遗忘阈值，每天按固定数量主动发题，发过即去重，发题后接费曼检验闭环**。

核心循环：

```
每日定时 → 检测遗忘指数（R）跌破阈值的题 → 按遗忘严重度取固定 N 道
  → 发题（新建会话）→ 标记"已发"去重 → 学生作答 → 费曼检验 → 回写 L2
  → 遗忘状态更新 → 次日检测自然排除已掌握/重新纳入仍遗忘的题
```

## 2. 与既有能力的关系

| 既有能力 | 复用方式 |
| --- | --- |
| `RecallPlan`（决策引擎） | 作为"检测遗忘"的输入源，找出 `due == true` 的题 |
| `review-recall` skill | 发题后的费曼检验，学生在新会话里作答 |
| `agentstore.CreateConversation` | 发题 = 新建会话（幂等，靠 request_id 去重） |
| `agentstore.Queries.Create` | 把发题消息作为新会话的第一条消息持久化 |
| 既有记忆提取链路 | 学生作答回写 L2（不引入裁定后门） |

**关键差异**：`RecallPlan` 是无状态检测器（每次现算 R 值）；防遗忘计划是**有状态的**——它要记住"哪些题已经发过"，避免每天重复发同一道题。

## 3. 数据模型（MySQL 新表）

### 3.1 `recall_plan`（防遗忘计划主表）

一个学生**一条活跃计划**，记录调度状态：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT PK | 自增 |
| `student_id` | VARCHAR(128) | 学生，ascii_bin |
| `status` | VARCHAR(16) | `ACTIVE` / `PAUSED` / `COMPLETED` |
| `daily_quota` | INT | 每日发题数量（固定，当前为 1） |
| `last_run_at` | DATETIME(6) | 上次调度时间，防重复触发 |
| `created_at` / `updated_at` | DATETIME(6) | |

### 3.2 `recall_plan_item`（计划条目 = 待发题）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT PK | 自增 |
| `plan_id` | BIGINT | 关联计划 |
| `question_id` | VARCHAR(36) | 题号（来自 L2 的 `question_ids`） |
| `topic` | VARCHAR(60) | 知识点（冗余，便于展示与去重） |
| `area` | VARCHAR(16) | 知识点大类 |
| `retrievability` | DOUBLE | 入队时的遗忘指数 R（快照，排序用） |
| `status` | VARCHAR(16) | `PENDING` / `SENT` / `REVIEWED` |
| `sent_at` | DATETIME(6) | 发题时间（`SENT` 时填） |
| `conversation_id` | VARCHAR(128) | 发题时新建的会话（`SENT` 时填） |
| `created_at` | DATETIME(6) | |

### 3.3 去重语义（关键不变量）

- 同 `question_id` 在**当前活跃计划**里最多一条 `PENDING` / `SENT` 记录，**绝不重复发**；
- 学生答完（`REVIEWED`）后，该题从"待发清单"移除；
- 若学生答错，遗忘状态未改善，**下一轮检测时该题仍会 `due`，可重新入队**（此时是一条新记录，不是复活旧记录）——这符合"没掌握就继续跟"的随访逻辑。

## 4. 关键流程

### 4.1 创建/维护计划（自动建单）

- **自动触发**：学生使用系统后，每当记忆提取完成（`memory.Service.AfterExtract` 钩子），自动检测该学生当前是否有题目遗忘指数（R）跌破阈值（`RecallPlan` 里有 `due == true` 的题）。
- **有 due 题 → 自动建单**：调用 `recallplan.Service.EnsurePlan`，若该学生尚无活跃计划，则 `UpsertPlan` 创建（`ACTIVE`，`daily_quota=1`）；已有计划则 no-op。
- **无 due 题 → 不建单**：`EnsurePlan` 直接返回，等下次记忆更新再检测。
- 不依赖模型引导、不需要学生确认——检测到即建，完全自动。

### 4.2 每日发题（调度）

后端自建调度循环（类似 `studentmemory.Service.Run` 的轮询，或每 N 分钟 `Step` 一次）：

1. 找出 `last_run_at` 早于"今天计划发题时刻"且 `status=ACTIVE` 的计划；
2. 对每个计划：`RecallPlan` 现算当前 `due` 题 → 与 `recall_plan_item` 里已有的 `PENDING`/`SENT` 求差集 → 得到"新到期且未发"的题；
3. 按 `retrievability` 升序（遗忘最严重优先）取 `daily_quota` 道；
4. 逐题发题：新建会话 → 写入发题消息 → 标记 `SENT` + 记 `conversation_id` + `sent_at`；
5. 更新 `last_run_at`。

### 4.3 发题动作（新建会话 + 模型生成开场 + 预置 user 消息）

对每题：
- `CreateConversation(student, requestID)` 新建会话（`requestID` 用题号+日期派生，保证幂等）；
- **服务端同步调大模型**生成个性化开场消息：输入该题题干 + 知识点 + 学生近期遗忘状态，产出自然语气开场（抛出题目 + 引导费曼式自述/拍照，**不含答案**）；
- 将模型生成的开场消息作为**该会话的第一条 user 消息**预置写入（复用 `agentstore.Queries.Create`），学生打开会话后 Runtime 自然接手、review-recall 模型引导作答；
- 标记 `SENT` + 记 `conversation_id` + `sent_at`。

> 落地方式说明：之所以"预置 user 消息"而非"直接写 assistant 开场"，是因为 `agent_message` 里 assistant 消息只能由 Runtime 的 `Finish` 在真实 turn 中 seal（有 version/position/prefix_hash/receipt 严格校验）。发题场景没有学生 user 输入，无法承载一条合法的 assistant 开场；预置 user 消息则完全复用"新建会话 + 首条用户输入"的既有流程，零架构风险。

### 4.4 检验与回写（接续 review-recall）

- 学生在新会话作答 → 走 `review-recall` 费曼检验（文字自述/拍照）；
- 作答作为普通轮次进入 `agent_message` → 既有提取链路 → 服务端裁定回写 L2；
- 该 `recall_plan_item` 标记 `REVIEWED`（从待发清单移除）。

**MarkReviewed 的判定时机**：挂在记忆提取完成的 `AfterExtract` 钩子（`recallplan.Service.OnExtract`）。逻辑：

1. 记忆提取完成 = 学生有**实质作答**且已被服务端裁定（`BuildMonth` 只处理 SEALED、学生自答的轮次）——这正是"有实质作答"的客观证据，而非"随便回了句话"；
2. `OnExtract` 拿到本次提取涉及的 `conversation_id` 集合，查出该学生 `SENT` 状态且会话命中该集合的题 → `MarkReviewed`；
3. 答错的学生，其遗忘状态未改善，该题下次检测仍 `due`，作为**新记录**重新入队（"没掌握继续跟"）。

## 5. 定时调度的实现选择

**结论：后端自建调度，不用 WorkBuddy automation。**

- WorkBuddy automation 是"定时唤起 Agent 执行 prompt"，不适合做生产级、确定性的产品发题调度；
- 采用与 `studentmemory.Service.Run` 同构的**轮询循环**：`Run(ctx)` 内 `Step(now)` + 15 秒 tick，`Step` 里判断"是否已到今日发题时刻 + `last_run_at` 未更新"。
- "每天特定时机"用 `daily_quota` + 配置的发题时刻（如每日 19:00）控制，`last_run_at` 防止同一天重复发。

## 6. 已定决策

1. **发题时刻**：每天 19:00（晚间学生有空）。
2. **每日数量**：**1 道**。
3. **计划生命周期**：长期 `ACTIVE`，每日动态补新到期题（题发完不终止计划）。
4. **答错重发策略**：`REVIEWED` 且答错的题，下次检测仍 `due` 时重新入队（"没掌握继续跟"）。
5. **发题消息形态**：**服务端同步调大模型生成个性化开场**（结合学生近期状态 + 该题知识点，自然语气抛出题目并引导费曼检验），**不写死模板**。生成后写入新会话。

## 7. 不变量

1. 同一 `question_id` 在当前活跃计划内最多一条 `PENDING`/`SENT`，绝不重复发。
2. 发题动作幂等：同题同日期重复触发，`requestID` 去重，不产生第二个会话。
3. 每日发题数 ≤ `daily_quota`，`last_run_at` 保证每天最多触发一次。
4. 检验与回写走既有记忆链路，计划层**不直接改 L2**，只标记 `REVIEWED`。
5. 发题消息**不含答案**，答案仅供后续 `get_review_question` 对照。
