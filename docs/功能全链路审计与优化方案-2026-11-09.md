# 项目全链路审计与优化方案

日期：2026-11-09。依据：当前代码、使用指南、现有真实模型验收记录、本轮隔离数据库复现及真实记忆提取样本。

## 1. 结论

目前是“主要路径可运行，数据语义与异常闭环仍有缺口”。解题事务、原文留存、引导首题隐藏答案已有可靠基础；长期记忆不应只以“生成了一份文档”验收，防遗忘也不应只以“成功发出一次题目”验收。画像合理性、首次自然到期、错误后的再复习、提取故障恢复需要优先修复。

| 功能 | 当前判断 | 已有基础 | 主要缺口 |
|---|---|---|---|
| 解题 | 文字主路径已跑通；真实成功率尚未系统量化 | 原始问题持久化、结构校验、模型数学复核、事务提交、回执幂等、历史修复 | 普通解题仍可能提前结束；图片/OCR需要重新专项验收；请求断开影响执行 |
| 长期记忆 | 正常路径可生成，存在会丢失更新的确定缺陷 | SEALED师生轮次提取、来源引用、L1由L2确定性生成、Redis原子发布 | 聚合更新丢失、摘要字符限制不一致、跨存储故障通知丢失、图片作答证据缺失 |
| 学生画像 | 能展示，但不能视为准确掌握判断 | L0手填资料、知识大类/能力白名单、时间衰减 | 提示后答对被判独立掌握、档位只升不降、自由命名知识点难合并、跨月状态重置 |
| 防遗忘提醒 | 发送样例成功，持续随访闭环不完整 | 计划表、队列、发题、绑定原题的review模式、作答后记忆提取 | 首次到期漏发现、UTC时区、已复习题永久去重、过期队列仍发送、失败恢复不充分 |

## 3. 需要优先修复的确定问题

### F1：同批知识点聚合可能丢失更新（P1）

位置：internal/modules/student/memory/service.go:230、319。

byKey保存切片元素的指针，随后向同一区域的Topics追加元素，切片扩容后原指针可能指向旧数组。之后更新已存在的知识点，写到了旧数组，最终输出没有变化。

复现：A答错 → 新增B → A独立答对。同批最终A仍为familiar、error_count=1，第三次作答时间及题号也没写入。

方案：先以map[topic_id]*Topic维护唯一状态对象，聚合结束后生成有序切片；或保存稳定索引并在访问时重新定位，不保留会扩容切片的元素指针。验收必须覆盖A、B、A交错、多区域、已有文档再新增知识点。

### F2：摘要“2000汉字”与“2000字节”冲突（P1）

位置：internal/modules/student/memory/service.go:199、taxonomy.go:155；internal/adapters/model/bailian/student_memory.go:55。

提取提示允许2000汉字，两处校验却使用len(string)>2000。700个常见汉字约2100字节，已在复现中被拒绝。这会造成正常模型输出反复提取失败。

方案：统一字符限制与字节预算，两处同时修改；提示、输出token预算和最大topics数量配套约束。对摘要过长与模型JSON截断给出可修订错误，避免无限重试同一无法容纳的批次。

### F3：画像保存成功，复习完成通知可能永久丢失（P1）

位置：internal/modules/student/memory/service.go:115、151。

Redis发布后才确认MySQL，再调用AfterExtract。若Redis成功、SQL确认失败，重试时fresh为空，会跳过用于生成通知会话集合的逻辑，随后确认成功却没有相关会话通知。复现中提取只调用一次，重试成功，但notified_conversations为空。SQL确认成功后进程在回调前退出，也存在同类窗口。

方案：记录可重放的“记忆已发布/复习证据已接受”事件，带学生、question_id、attempt_id、来源轮次和判定结果；用持久化事件待办及幂等消费替代一次性回调。跨MySQL与Redis不假设单事务，依靠发布修订号、确认及对账恢复。验收在发布前后、确认前后和通知前后逐点注入失败。

### F4：没有计划的学生，首次自然到期可能永远不被发现（P1）

位置：internal/modules/teaching/recallplan/service.go:79、122、204。

EnsurePlan只挂在提取完成后。刚学完R很高时不建计划；随后学生不再产生提取，Step只扫描已有ACTIVE计划，无法发现这名学生已到复习时间。

复现：首次检查无due，不建单；把服务时钟推进7天，Step后仍无计划，遗忘检测只在最初调用过一次。

方案：有有效学习证据时即登记持续监测对象，或维护每个学生的next_due_at并定期扫描。到期发现不能依赖学生再次来聊天，也不依赖模型主动决定。

### F5：默认19点实际按UTC执行（P1）

位置：internal/adapters/persistence/mysql/recallplan/repository.go:161；recallplan/service.go:253、278。

DuePlans使用now.UTC().Hour()与UTC日期，而请求去重日期又取now.Format，存在两套日历口径。

复现：上海19:00没有到期计划；上海次日03:00才会命中UTC19:00。

方案：计划存timezone（当前默认Asia/Shanghai），计算当地send_hour及当地run_date，再转换为UTC时间戳存储；查询、去重键、配额、MarkRan使用同一日历。覆盖跨日和服务重启。

### F6：已复习的题不能再次入队，违背持续随访设计（P1）

位置：internal/adapters/persistence/mysql/recallplan/repository.go:60—70。

AddItems对同一plan_id/question_id的任何历史记录都去重，包括REVIEWED。复现：PENDING→SENT→REVIEWED后再次添加，added=0。

结果：答错后不能重新跟进；即使这次答对、几天后再次遗忘，也不会再次发同题。使用指南“答错会继续跟进”与实际实现不一致。

方案：引入review_cycle_id或scheduled_attempt_id。只对当前活跃周期PENDING/SENDING/SENT去重，历史周期允许追加；每周期设置next_due_at和最小间隔，防止答错后同日轰炸。不能仅删除SQL中的历史去重条件，现有唯一键也需配套迁移。

### F7：已恢复掌握的旧队列任务仍可能被发送（P1）

位置：recallplan/service.go:223—244；mysql/recallplan/repository.go:81。

调度追加当前due题后，直接取所有历史PENDING发送。没有重新验证这些任务今天是否仍due；排序用的也是入队时R快照。

复现：当前due清单为空，旧PENDING仍被成功发送一次。

方案：发送前以最新question/topic状态再验证；不再到期则取消/延期，题目已删除或不可读则移出队列并记录原因；重新计算优先级。不能只累加新任务。

### F8：画像会把提示后完成误判为独立掌握（P1，真实模型样本）

位置：bailian/student_memory.go:50—58；memory/service.go:236起。

authored、是否犯错及suggested主要仍由模型判断，服务端做的是枚举、引用、部分一致性和聚合校验，并未真正证明“独立完成”。本轮明确给出“教师提供公式、学生依提示完成”的旧摘要，模型依然输出mastered。

同时，提示把“需提示=partial”和“partial必须incorrect=true”绑定在一起，混淆了“需要帮助”与“数学上答错”。

方案：在问答过程中记录attempt_id、hint_level、help_given、student_attempt、correctness、reasoning_complete、copied_or_rephrased、evidence_refs。提示依赖由系统可见事件约束，不能只让模型从聊天摘要猜。答案正确与独立掌握分开；得到提示的当前练习可记为“提示后完成”，独立掌握需另一次无提示证据。

### F9：图片作答缺少可供记忆提取的学生OCR正文（P1，静态链路缺口）

位置：mysql/studentmemory/repository.go:221—239；bailian/student_memory.go:26—30；teaching/review/review.go的recognize_review_image。

复习工具能识别学生上传步骤，但长期记忆组装会过滤工具结果，提取器只消费User/Assistant/QuestionText。只上传图片时User可能只有“[图片题目]”，QuestionText又可能是原题题干，而非学生手写作答。提取器没有消费该作答图片的OCR文本。

方案：保留过滤普通工具日志的原则，单独发布有来源和用途的student_attempt_ocr证据，绑定本轮asset_id、question_id、OCR版本与确认状态。未识别或未确认时不生成确定掌握结论。

## 4. 画像语义、性能及体验问题

### 4.1 掌握度不是当前能力

memory/service.go:289只保留更高掌握档。同月先mastered、后明确答错，复现仍为mastered，error_count却为1。若想保留历史最佳，可另设best_mastery；页面“已掌握”应来自current_mastery及证据置信度。不要把“曾经答对”显示成“现在可靠掌握”。

error_count在答对后清零，而profile.js显示“累计出错”，口径不一致。应区分总错误数、近期错误数或连续错误数。

### 4.2 月归档不应重置学习状态

BuildMonth只从同一个月的old文档继承状态；新月份首次出现同知识点又使用默认稳定性。RecallPlan只是选择last_seen较新的月份，不累计两个月的更新。这意味着月界会改变学习状态的累计口径。

建议维护跨月的规范知识点状态投影，月文档用于快照与证据归档；历史回放能重建同一状态。先明确按attempt顺序更新，再考虑更复杂的遗忘算法。

### 4.3 知识点名称不能充当唯一身份

目前key是area+'/'+模型自由填写的topic。真实样本同属等差数列，分别写出“通项与求和公式”“通项公式an=…”“通项与求和应用”，可能成为多个互不关联条目。

建议topic_id使用维护的细粒度目录，显示名允许变化；模型只能引用目录或提出待审核映射，不能凭自由名称新建身份。

### 4.4 题号必须来自真实作答来源

memory/service.go:271直接把et.QuestionID追加到来源题号列表。本轮复现接受了不属于来源的虚构题号。应完全从已验证SourceIDs推导question_id，或要求模型题号与绑定来源一致；模型不拥有生成题号的权力。

### 4.5 遗忘数值是启发式估计

taxonomy.go使用固定增减和指数公式，并未看到学习数据拟合或校准。R在elapsed=0时总是1，即使刚答错。因此100%不能解释成“学生有100%概率答对”。稳定性合法取值0又被读取逻辑当成“缺失值”重置成0.5。

建议UI区分“掌握证据”与“预计记忆保持度”，标明估计；缺失使用可空字段或schema迁移识别，不能借0值判断。先收集真实无提示复习结果，评估校准后再决定是否升级算法。

### 4.6 只看答案，不应自动形成能力画像

当前authored=false会跳过Topic更新，这是合理保护。只输入问题、阅读教师解析，可能只有原始记录及摘要，没有可判断的掌握数据。指南“日常搜题就积累盲点”过度承诺。

建议分开记录“接触过哪些题/知识点”和“实际表现如何”；未知掌握状态保持未知，安排低负担诊断题补证据。

### 4.7 提取触发与界面反馈

10轮/新会话/闲置2小时才提取，用户完成一次引导后画像可能很久不更新。可以在一道题有效作答结束或一次复习完成时，优先提交该题的增量证据；重摘要仍按批次处理。页面显示最近画像更新时间、待处理作答数及“正在更新”，不要统一显示“已同步最新学习状态”。

### 4.8 避免为了读L2反复加载L3

RecallPlan扫描最多120个月，逐月Documents.Load；后者同时MGET并解析L1、L2和完整L3。教师每轮预载又调用RecallPlan，历史大时会消耗明显内存和时间。

建议增加只读L2的接口/当前知识状态投影；L3按来源取证、分块读取。缓存带revision及next_due_at的遗忘清单，不在每轮聊天扫描全部历史。

### 4.9 提醒的发送可靠性与可见性

调度没有计划/任务领取租约，多实例下配额靠“查后写”不足以保证；某题失败也会MarkRan，可能直到次日才再试。会话与首条消息分步写入，当前重试可借已创建会话补写消息，但仍需覆盖创建后退出、消息写入后退出、MarkSent失败等故障点，不能只验证正常投递。

建议任务领取与状态SENDING、唯一投递键、受配额约束的当天重试、消息写入确认。题干取不到不能发送空题。开场由老师产生却预置为user消息，应增加system_delivery/assistant_opening来源类型，避免混入学生自答。

当前网页主要启动时restoreSubmissions，新建提醒会话不等于已打开页面实时收到提示。应增加学生事件订阅、未读入口及投递/已看/已作答状态。手机推送仍是另一个尚未实现的渠道。

### 4.10 引导的工具权限还需按当前阶段约束

guideTool检查题号绑定，但review.Module在所有轮次贡献get_review_question，后者只检查题目属于当前学生，没有检查当前绑定题号。引导中因此存在读取其他自有题答案的能力。reveal_solution也没有客观的“已完成推导”状态前置，当前主要由提示词与少量输出关键词约束。

建议按任务阶段提供工具、绑定question_id/asset_id，并用真实的作答评估结果控制最终对照展示。关键词拦截无法覆盖所有自然语言答案；结构化输出应区分question/hint/feedback/final_check。

### 4.11 解题与OCR验收应单独量化

正式保存回执、事务失败不留半份结果、重复请求核对已有回执的设计值得保留。当前工具强制仅在引导首题启用，普通新题仍可能用普通文字提前结束。应统一“必须正式提交”的任务完成约束，并区分信息不足需澄清与技术失败。

数学复核仍是模型复核，不是正确性的证明。文字题、公式识别、缺条件题、配图题、数学错误、长历史、同题重试应各有固定样本集；记录首次成功率及人工核对准确率。此前OCR真实样本出现过公式断行错误，本轮不能据模拟测试通过宣称拍照链路已稳定。

## 5. 引导首问为什么慢

当前路径是串行的：

```mermaid
flowchart LR
  A[学生选择引导并提交] --> B[保存原题]
  B --> C[教师读取Skill和题目]
  C --> D[生成完整答案与元数据]
  D --> E[校验并按需修订]
  E --> F[正式提交]
  F --> G[前端收到guide_start]
  G --> H[前端另发一次请求]
  H --> I[教师生成第一问]
```

位置：httpapi/solve.go:47、69、95、104；web/app.js:546—553。

首问等待时间≈准备与读取工具的多次模型调用＋完整解答生成＋复核＋修订＋提交＋第二次引导请求。隐藏答案不会省掉生成答案的耗时。

已有真实记录中：一次包含提交、自动首问及刷新恢复的前端真实集成测试约20.5秒；原数列题带一次字段修订的解题调用约32.6秒，尚不包含后续首问。这些是单次样本，不是P50/P95，也不是所有题的性能承诺。

当前引导首题还屏蔽了progress事件，用户主要看到心跳和等待；教师首问依赖浏览器再发一次请求，关闭页面可能留下“答案已准备但第一问没生成”的状态。

## 6. 异步引导方案

### 6.1 先确定可改变的产品约束

| 方案 | 首问前必须保存完整答案 | 首问速度 | 可靠性与代价 |
|---|---|---|---|
| 现状同步 | 是 | 等待完整求解 | 浏览器连接承载执行 |
| 持久化后台任务、就绪后提问 | 是 | 本质上仍等完整求解 | 刷新/断线可恢复，进度更清楚 |
| 先问安全的起步问题，后台准备参考答案 | 否；最终核对前必须已保存 | 可明显提前开始思考 | 需任务状态、作答队列与展示权限；建议采用 |

如果严格坚持“任何问题出现前，答案就必须保存”，异步只能改善恢复能力和等待提示，不能消除这一先后依赖。要缩短首问，需要允许准备期间先问不依赖标准答案的问题。

### 6.2 推荐的学生体验

1. 提交后立即确认题目已接收，显示“参考解答准备中”。
2. 对文字题，教师先问一个无需标准答案即可提出的问题，如“题目给出了哪些量？你准备先求哪一个？”此时不宣称已校验或已保存答案，也不判断学生结论是否正确。
3. 同一教师在后台继续完成math-solve：完整答案、知识点、难度、校验、提交回执。
4. 学生可先写思路；参考答案未就绪时先保存作答。可以明确提示还在核对参考解答，避免用尚未校验内容给确定性判分。
5. 答案准备好后，继续针对学生真实作答提出下一问。完成推导后再按权限读取正式答案作对照。
6. 若后台失败，保留题目、第一问和学生作答，显示可恢复状态；不把草稿当正式答案。

图片题必须先获得可靠OCR题干。OCR完成前可以确认收到图片并报告识别进度，不应基于未识别条件发出具体数学提问。

### 6.3 保持“只维护一个智能体”

仍保留一个teacher定义、一个系统身份，math-solve、step-tutor、review-recall及memory由它按上下文选择。后台任务执行的是同一教师定义，不新增solver教师、guide教师或planner智能体。

推荐首版采用同一会话串行执行：

- 开场轮先完成并封存第一问。
- 后台参考答案任务随后领取该会话执行权。
- 新学生作答可以持久化排队；参考答案任务完成后再运行后续引导轮。

这样可利用学生思考时间准备答案，避免当前会话单活跃租约与多段历史快照互相冲突。必须明确“一个智能体定义”可以有不同任务运行，并不是由前端并发调用两个互不相干的教师。

如果未来要求参考答案准备时也能持续即时判题，则需独立任务执行上下文和租约、共享经验证的题目版本，再做并发；这不是首版最小改动。

### 6.4 必要的工程改动

- 新增持久化teaching_task：task_id、student_id、conversation_id、source_message_id、input_revision、mode、status、lease、attempt_count、next_retry_at、error_code、question_id及solution_id。
- 明确可用性状态：RECEIVED、INPUT_READY、REFERENCE_PREPARING、REFERENCE_READY、FAILED；first_question_published单独记录，不把“已问首问”等同于“参考答案已完成”。
- 原题身份在接收时就分配，不再要求必须有正式solution才能进入起步提问。当前Guide模块依赖已提交题号，需增加只提供题干/输入状态的读取能力。
- 参考答案任务显式引用原始用户消息。内部任务不能伪造为学生作答；当前Service.Input要求输入记录与运行turn一致，需增加受服务端约束的任务来源绑定。
- POST提交原题与任务在事务内落库，返回task_id。提供任务状态查询和可重放事件流；SSE断线只影响订阅，不取消任务；重连依据event_id补读。
- 第一问也由任务处理并保存，不能仅依靠浏览器收到guide_start后再启动。
- worker使用任务租约和幂等键；提交按task/input_revision唯一。重生成是新版本任务，重试是同一任务，语义分开。
- 更新题目后废弃旧revision；旧后台结果不得覆盖新题。会话删除/任务取消要阻止迟到结果再次展示，并处理待提取证据。
- 前端用task_id跟踪状态，可显示安全阶段进度；不下发draft、答案、解析与校验敏感细节。参考答案未就绪仍可保存学生草稿，避免一个全局sending锁把输入框长时间锁住。
- 只对正式、可归因的学生作答发布记忆证据。后台生成答案、系统开场、排队确认均不能累计学生独立表现。

单纯在HTTP里加go func并继续使用请求Context不能解决这些问题：请求取消、服务重启、重复任务和同会话租约都需要处理。

### 6.5 先做低成本提速

- 恢复引导首题安全的阶段进度，仅输出“识别中/准备中/校验中/已准备”，不输出答案草稿。
- 按本轮任务注入简短、版本固定的技能及输入背景，减少机械重复read_file和独立读取目录的模型往返；不能缓存错学生或错题的动态数据。
- 缓存客观知识目录、同一asset/version的OCR结果以及已有提交回执。
- 普通读取画像不要加载完整L3。
- 记录received_at、first_question_at、reference_ready_at、student_attempt_at、checked_at、completed_at，按文字/图片、题型、是否修订统计P50/P95。

可设置“1秒内确认接收，简单文字题首问目标5—8秒”的试运行目标；这只是待压测目标，当前没有性能证据保证达到。

## 7. 建议实施顺序与验收

### 第一批：先保证学习状态与提醒正确

修复F1聚合、F2摘要限制、F3可靠通知、F4首次到期、F5时区、F6复习周期、F7发前复核；新增图片作答证据绑定。每项都有可重复的测试，不只用正常路径样例。

### 第二批：重建有证据的画像

增加规范topic_id、attempt证据、提示依赖、current/best_mastery区分；修复跨月状态与0值迁移；校正“累计错误”“可回忆概率”等页面口径。用真实模型评测集检验“只看答案”“提示后答对”“抄写答案”“独立答对”“后来答错”，并对照人工标注。

### 第三批：持久化异步任务与提前首问

先落任务/事件/重连机制，再开放安全首问与作答排队。保持一个教师定义，按题目任务串行持有租约。

| 场景 | 必须满足的验收结果 |
|---|---|
| 首次学完、此后无任何聊天 | 自然到期仍能发现并创建复习任务 |
| 上海19:00与跨日 | 按同一当地日历发题，不在03:00误发 |
| 答错、已复习、再次到期 | 可新建复习周期，且当天不过量 |
| 已掌握、旧队列仍存在 | 发送前取消/延期旧待发任务 |
| A→B→A交错及跨月 | 不丢更新，状态不因扩容或月界重置 |
| Redis成功、SQL失败、回调前退出 | 不重复增加掌握证据，不丢复习回写事件 |
| 提示后最终答对 | 记录帮助依赖，不判独立掌握 |
| 只上传作答图片 | OCR证据可追溯；无可靠证据时维持未知 |
| 引导准备中刷新/断网/服务重启 | 任务可恢复、第一问可恢复、不重复提交 |
| 学生很快提交下一步 | 作答保存并关联原题，不与后台任务抢租约 |
| 重生成、修改原题、删除会话 | 不串版本、不展示迟到答案、不误写画像 |
| 正式准备失败 | 明确状态并保留作答，不提前发布正式答案 |

## 8. 使用指南需要同步更新

当前使用指南仍写“引导学习待开放”，与实现不符；“答错后重新入队”“上海晚间发题”等文案与当前逻辑不符；仅阅读教师答案不能产生可靠掌握画像。解答重新生成不等于完整版本管理，站内生成复习会话也不等于手机推送。

此外，“数据尚未接入云端”不准确：本地存储与模型/OCR服务调用是两件事，代码会向配置的模型服务发送相应输入。应据实际部署描述数据流，不能只依据服务监听127.0.0.1推断全程本地。

建议在对应缺陷修复并验收后更新指南状态；本次没有直接把计划中的能力写成已实现。
