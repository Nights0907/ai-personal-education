# 学生档案消费：复习决策层与四个下游方向

版本：v1.0
日期：2026-11-03
前置：`docs/学生档案与长期记忆数据形态.md`（L0—L3 提取与存储）、`docs/学生档案遗忘维度设计.md`（HLR 遗忘模型）。

## 1. 背景与定位

一期搭建了智能体 Runtime 与解题服务（题目信息入 `teaching_*` 表、会话消息入 `agent_message`）；二期建成了学生档案 L0—L3，并引入遗忘维度（`stability` / `difficulty` 落盘，`retrievability` / `due` 读取侧派生）。

但截至二期，档案的**唯一消费方式**是「被动等待模型想起来去读」：`Contribute` 把 L0+L1 塞进上下文、挂两个只读工具（`read_student_memory` / `list_student_memory_indexes`），由模型按需取用。`retrievability` / `due` 算出来了，却没有任何代码用它做决策。

本文定义**消费层**：把「算出来的遗忘状态」变成「驱动下游能力的决策」，并给出四个下游方向如何复用同一决策引擎。

## 2. 核心：RecallPlan 决策引擎（发动机）

新增 `Service.RecallPlan(ctx, student, now)`（`internal/modules/student/memory/recall.go`），是四个下游方向共用的唯一决策入口。

### 2.1 输入 / 输出

- 输入：`student_id` + `now`。
- 输出：`RecallPlan{StudentID, Items, DueCount, DerivedAt}`，`Items` 为 `RecallItem` 列表：

| 字段 | 含义 |
| --- | --- |
| `area` / `topic` | 知识点大类 / 子知识点 |
| `mastery` | 掌握档位（unseen/familiar/partial/mastered） |
| `ability` | 能力维度 |
| `error_count` | 犯错次数 |
| `last_seen` | 最近一次有证据作答时间（遗忘的时间锚点） |
| `retrievability` | 可回忆概率 R（读取侧派生，不落盘） |
| `due` | `R < 0.80` 时 true，表示已到复习窗口 |
| `question_ids` | 证据题号 |

### 2.2 跨月聚合

`RecallPlan` 扫描学生**所有月份**的 L1 索引（`Documents.Indexes`，上限 120 月），逐月 `Load` L2，按 (`area`,`topic`) 合并：

- 同 topic 跨月出现，取**最新 `last_seen`** 的月份为证据，`mastery` / `error_count` 以最新月份为准；
- `question_ids` 跨月取并集；
- 遗忘锚点（`stability` / `difficulty`）零值回填中性先验（与 `recallView` 一致）。

### 2.3 排序（遗忘优先级）

```
due 优先 → 其次 retrievability 升序（遗忘越严重越靠前）→ 最后 (area,topic) 字典序
```

**注意**：排序按 `retrievability` 而非「距离上次作答的天数」。遗忘模型里「熟练但久远」（高 stability）的知识点，可能比「近期学过但困难且反复错」（低 stability、高 difficulty）忘得更慢——后者 R 更低、排更前。这是 HLR 模型的正确语义。

### 2.4 边界

- **只读**：`RecallPlan` 不写任何文档；`retrievability` / `due` 由落盘锚点相对 `now` 现算。
- **不替代 `read_student_memory`**：决策层给「结论清单」，读单个知识点/月度的证据原文仍走 `read_student_memory`。
- **失败降级**：调用方（如 `Contribute`）把 `RecallPlan` 当 best-effort，出错不阻塞本轮。

## 3. 四个下游方向（同一发动机的四个输出口）

| 方向 | 消费 `RecallPlan` 的哪部分 | 现状 |
| --- | --- | --- |
| **复习提醒 / 召回** | `due == true` 的 `Items` | 对话开场注入已实现（见 4）；手机通知预留接口 |
| **对话内自适应** | 全量 `Items` 的 `mastery` + `retrievability` | 复用 `Contribute` 注入，讲解深度/提示强度由模型依据掌握度调整 |
| **画像报告 / 看板** | 全量 `Items` 的分布与趋势 | 数据已就绪，前端可视化待建 |
| **个性化选题** | `mastery` + `difficulty` + `retrievability` 组合 | 待实现（需选题库 + 推荐逻辑） |

## 4. 已实现：对话开场注入复习提醒 + 费曼式复习检验

`Module.Contribute`（`registration.go`）在预加载阶段调用 `RecallPlan`，把 `due == true` 的知识点（最多 8 个，含 `question_id`）注入 `LongTermMemory` 的 `due_review` 字段，`usage` 中提示模型「读取 review-recall 技能，用 get_review_question 按题号取回原题，引导学生费曼式自述/拍照，对照标准答案检验，不直接甩答案」。

- 受 6000 字节上下文预算约束，超限时**优先裁减 `due_review`**，再裁 L1 索引、最后裁 L0 学习目标；
- `RecallPlan` 失败时 `due_review` 为空，不影响本轮。

### 4.1 复习检验闭环（review-recall skill）

核心洞察：**只提醒知识点是低效的「再认」，让学生重做当时的原题才是有效的「提取练习」**。复习提醒因此升级为完整闭环：

```
遗忘节点触发 → RecallPlan 给 due 知识点 + question_id
  → get_review_question 取回原题 + 标准答案（答案不展示给学生）
  → 学生文字自述思路 / 拍照上传解题步骤
  → 模型按费曼法对照判定（思路是否自洽、推导是否完整、能否讲清）
  → 反馈引导（partial/incorrect 给最小提示，不直接甩答案）
  → 学生作答作为普通对话轮次进入既有记忆提取链路，服务端裁定回写 L2
```

新模块 `internal/modules/teaching/review/`（`review-recall` skill）：
- `get_review_question` 只读工具：复用 `solve.Repository.Get(ctx, student, questionID)`，按题号取回原题与标准答案，**天然按 student_id 隔离**，不跨用户。
- 判定在**模型对话内**完成（答案作为工具返回值供模型对照），不新增服务端判定流程。
- **不直接更新档案**：学生作答走既有 `agent_message → Notify → BuildMonth → 服务端裁定` 链路回写 `mastery`/`stability`/`error_count`，不引入裁定后门。
- 拍照输入：复用 `photo` 模块 OCR 能力（本期 SKILL 已声明，工具接入待接）。

## 5. 预留：手机通知（未接真推送）

系统当前**无推送基础设施**（无小程序、无短信、无原生 App）。`RecallPlan` 的 `Items` 已结构化输出 `due` 复习清单，未来接推送时直接消费即可：

- 微信小程序订阅消息（`mini-program-development` + `cloud-service`）是最可能的落点；
- 推送任务只需：定时/触发 → `RecallPlan` → 过滤 `Due` → 生成提醒文案（附原题）→ 调订阅消息接口。

本轮**不接真推送**，只保证数据就绪。

## 6. 不变量与约束

1. `RecallPlan` 只读不写，遗忘参数全部由落盘锚点现算。
2. `due` 判定统一走 `IsDue(Retrievability(...))`，阈值 `τ=0.80`（见遗忘维度设计）。
3. 消费层**不绕过**服务端裁定：`mastery` / `error_count` 仍是 L2 里已裁定的值，消费层只读。
4. 上下文注入始终受预算约束，`due_review` 优先让位，不挤占 L0/L1 基本信息。
5. 复习检验**不直接改档案**，判定结果经既有提取链路服务端裁定回写，不引入后门。
6. `get_review_question` 只读、按 student_id 隔离，答案仅供模型对照、不展示给学生。
