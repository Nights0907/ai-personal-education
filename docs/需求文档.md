累计 10 轮尚未提取的成功问答、新建服务端会话、距学生最近输入满 2 小时，任一条件触发异步提取。新建会话触发此前尚未提取的历史；首次创建空会话不调用模型。计数按学生跨会话累计，一轮是完整成功的 user＋assistant；失败和工具中间态不计数。后台约每 15 秒检查，并在成功轮次和创建服务端会话后唤醒。

## v8.0 MCP OCR 交付

链路：网页上传 → 保存原图 → Agent Store 保留原始备注与图片引用 → 原有四节点图 → math-solve Skill → recognize_input_image → MCP OCR → 缓存 OCR → validate_solution → finalize_solution 事务入库 → 正式回执展示与历史修复。

真实联调：合成图片“解方程 2x+3=7，求x。”识别为“解方程2x+3=7，求x。”，经百炼解答和独立复核得到 x=2，原图/OCR路径及答案/解析/步骤均已保存。该样例不替代手写、复杂公式和数学质量评测。

一期只支持清晰完整、无需理解配图的单题；JPG/PNG/WebP，最大5MiB、4000万像素。不包含多题切分、图形理解、人工 OCR 修订。失败保留原图及待回答消息，无正式回执不宣称完成。

学生可上传图片，可选填写备注。网页展示原图、OCR原文与正式解答。图片备注是原始消息，解题依据是OCR题干，不能由备注补造图形条件。同一学生相同文件复用资产，同资产同配置复用成功识别；新请求仍可形成新解答，目前不做跨新请求的数学重复题合并。二期个性化教学与三期RAG范围不变。

## 既有方案（历史实施状态以v8.0章节为准）


## 1. 产品目标与三期主线

产品从“获得解答”逐步发展为“理解方法，并能独立迁移”。

| 阶段 | 核心目标 | 学生能完成的事情 | 本期成功的判断 |
|---|---|---|---|
| 一期：解题与沉淀 | 解得出来、存得正确、找得回来 | 文本或照片提交单题，查看完整解答，在个人题目记录中回看 | 解答质量合格；输入、题目、解析与资源准确关联；重复请求不产生重复记录 |
| 二期：个性化教学 | 了解学生、解释到位、验证理解 | 维护学习信息，获取适合自己的解析，选择卡点接受引导，用自己的话讲解并接受追问 | 个性化有可解释依据；辅导能推进；理解判断有具体作答证据 |
| 三期：题库与迁移 | 找到合适的下一题 | 检索同类题、解法相似题和补薄弱点的题，选题练习 | 返回真实且适合的题库题，来源与相似理由可追溯 |

一期不提前开发学生画像、引导式问答或费曼验证。二期不以公共题库、RAG 或大规模练习系统作为上线依赖。三期新增题库和检索能力，复用前两期的题目结构与学生证据。

默认仍直接展示完整解答。引导学习在二期作为学生可选入口；数字形象、语音和口型动画不属于已确认范围。

## 2. 决策状态与范围约束

### 2.1 已确认

- 一期：文本解题、拍照解题、题目信息正确存入数据库。
- 二期：学生个性化信息收集、引导式问答、个性化解析、费曼式教学验证。
- 三期：自有或已授权数学题库、RAG 检索与相似题匹配。
- 跨教材版本的统一高中数学知识体系，按主题、子主题、知识点组织。
- Go + Eino、云端模型 API、响应式网页、管理员发放试点账号；沿用小规模试点目标。
- 解答输出四项：答案、解析、解题步骤、知识点。错解选填。

### 2.2 本轮已确认的技术边界

| 问题 | 本轮确认决定 | 范围影响 |

## 3. 一期：文本与拍照解题、可靠入库

### 3.1 用户流程

登录 → 输入一道题或上传单题照片 → 可选提交自己的解答 → 识别与解题 → 校验并保存 → 展示四项解答与保存状态 → 从“我的题目”回看。

一期只采集必要账号信息。建议教学用的年级、学习目标、薄弱点自评在二期统一收集，不让首次解题被长问卷阻断；账号昵称/姓名是否必填由账号设计确认。

### 3.2 文本解题 P1-01

- 支持中文题干、数学公式、选择项和同一道题内的多个小问；题目与错解分开输入，错解选填。
- 支持选择、多选、填空、解答题；保留题干原文，不静默改变量、数值、正负号或不等号。
- 返回答案、解析、解题步骤、知识点；多小问答案与对应步骤准确关联。
- 解析解释思路与方法选择，步骤展示具体推导；必要定义域、适用条件和分类讨论不得省略。
- 使用高中可理解的方法与公式格式。用户可报告“答案或解析有问题”；反馈入口为建议项，不替代教师评测。
- 提交错解时一期保存原始内容，不要求建立画像或开展多轮教学。

### 3.3 拍照解题 P1-02

- 手机拍照或上传本地图片，预览后提交；一期每次一道题，一题含多个小问仍视为一题。
- 按已确认方案采用独立 OCR；模型接收识别文字与公式，原图作为题目资源保留。
- 当前范围为清晰、完整、无需理解配图语义的单题。纯文字描述充分的几何题可支持，依赖配图关系的题目不纳入当前验收。
- 印刷题目与手写错解识别分别评测；不能用通用手写文字识别指标替代数学公式评测。
- 支持图片格式、容量等上传校验，以及网络/OCR/模型失败后的重试。
- 沿用此前一期边界：不开发多题切分、模糊/缺条件识别、自动补题、手动 OCR 修正及重拍引导；页面明确支持范围。后续扩展须单独确认。
- 模型不能在条件不足时自行编造条件。服务无法形成合格解答时，保留任务失败状态，不把半成品标记为成功。

### 3.4 解答展示与版本 P1-03

| 区域 | 需要展示与保存的内容 |
|---|---|
| 原题 | 规范题干、选项/小问、原始照片引用；保留原始输入可追溯 |
| 答案 | 整题或各小问的最终结果、表达式或结论 |
| 解析 | 整体思路、方法与关键原理 |
| 步骤 | 稳定 step_id、顺序、小问归属、步骤标题、推导和公式 |
| 知识点 | 主知识点、辅助知识点、统一大纲编码与版本 |
| 状态 | 处理中、成功、失败、保存待重试等基础任务状态 |

重新解题产生新解答版本，不覆盖原版。二期引导绑定具体题目/解答版本；不能因重新生成导致旧步骤引用错位。模型返回的内部推理不作为学生可见解析或学习记忆保存。

### 3.5 正确入库 P1-04

“正确存储”同时包含内容结构正确、关联正确和提交一致性，不只是模型输出 JSON 能解析。

| 层次 | 一期要求 | 验收方式 |
|---|---|---|
| 原始内容 | 原文字、原图、原错解不被规范化结果覆盖 | 从提交记录回放并逐字段核对 |
| 结构化内容 | 题型、选项、小问、答案、步骤、知识点符合受控 Schema | 缺字段、未知知识点、重复步骤 ID 等用例被拒绝 |
| 数学内容 | 公式及关键条件没有因清洗/存储变形；答案与解析一致 | 教师评测；原输入、展示与回读结果比对 |
| 所属关系 | 学生、题目、输入、资源、解答版本和任务对应正确 | 跨账号与跨题目访问/写入用例通过 |
| 提交一致性 | 仅完整校验通过的解答成为正式成功结果 | 事务故障、重试与进程恢复用例通过 |
| 幂等 | 同一提交重试不重复建题、不重复创建作答 | 重复请求、超时回调、重复领取用例通过 |
| 可追溯 | 保存模型/提示/Schema/OCR 版本和来源引用 | 可定位原输入及所用解析版本 |

结构校验不能证明数学正确。模型答案不能直接写入正式题目记录；先校验候选，再提交冻结结果。

建议 MySQL 将题目、解答、步骤关联、提交成功状态和修复待办放在同一业务事务。图片已上传 OSS 后通过资源状态关联；数据库与 OSS 不宣称跨系统原子提交，异常资源通过待办重试清理。

### 3.6 我的题目 P1-05

- 解题成功后自动收录，提供列表、详情、按知识点/题型/录入时间筛选和基础关键词查询。
- 一题多知识点，指定主知识点用于默认分类。学生分类调整与标准知识标签分别保存。
- 完全相同的规范题干、选项、小问和条件可确定性合并；数值或条件不同的变式保留为不同题目。
- 每次真实提交及可选作答独立保留；网络重试不算一次新作答。指纹只用于查找候选，同题合并仍校验结构内容。
- 无法确定同题时不强行合并。一期去重不依赖向量检索；三期相似题也不能被自动当成同题。
- 删除题目时，按资源引用关系处理解答、提交和图片；不同学生的数据互不影响，删除后的后台旧任务不能重新写回。
- 产品采用统一的成功状态：可供展示的正式解答与数据库保存版本一致；业务提交后运行轨迹失败只修复轨迹。

### 3.7 一期不做

不生成薄弱画像，不做卡点引导、个性化解析、费曼验证、公共题库、RAG、相似题推荐、练习测验或全题型批改。保留字段/引用扩展能力，不建立空页面或伪入口。

## 4. 二期：学生信息与个性化教学

### 4.1 学生信息采集 P2-01

采用“少量主动填写＋学习过程逐步补充”。未填写偏好时仍可使用通用解答。

| 信息 | 采集方式 | 使用方式 | 证据属性 |
|---|---|---|---|
| 年级、当前学习主题 | 学生填写或选择，可修改 | 控制讲解深度与知识范围 | 学生自述 |
| 学习目标 | 例如理解概念、完成作业、复习某主题 | 调整本次教学目标 | 学生自述 |
| 基础与薄弱点自评 | 可选选择或简述 | 冷启动参考，不直接认定薄弱 | 待验证 |
| 表达偏好 | 详细/简洁、先思路/先步骤等 | 调整呈现形式 | 学生偏好，可随时变更 |
| 错解、引导作答、费曼解释 | 学习过程中形成 | 建立可解释的知识与能力观察 | 有具体来源的行为证据 |
| 帮助使用情况 | 是否看过答案、提示次数、示范、跳步 | 判断表现是否依赖帮助 | 系统记录 |

不把一次行为固化成长期“学习类型”。个性化信息与本轮目标冲突时优先尊重学生本轮选择，信息不充分时回退到标准解析。

### 4.2 学生档案 P2-02

沿用已讨论的可解释能力分类：概念理解、运算求解、逻辑推理、数学建模、图形与空间理解。只有支持范围内的真实证据才能触发对应判断；未启用图形理解时，不宣称诊断了依赖配图的空间能力。

每项画像包括：知识点/能力编码、观察结论、状态、对应题目与作答片段、建议关注（一般/中等/重要）、判定理由、最近证据发生时间。

- 仅提交题目、收藏、停留时间或选择某卡点，不足以认定能力薄弱。
- 自评与系统观察分别保存；证据不足时标记待验证，不制造确定结论。
- 重复上传同一错解不重复加重关注；不同题目的真实作答分别记录。
- 关注等级由教师审核规则聚合，不由模型任意打分。
- 最近出现时间取证据实际发生时间；访问档案不刷新该时间。
- 删除、纠正或撤销证据后重算画像，学生可查看判断依据并反馈异议。

### 4.3 引导式问答 P2-03

解答页点击“引导学习” → 选择卡点或默认第一步 → 教师逐轮提问 → 学生作答 → 反馈/提示 → 推进或补充解释。

- 起点尊重学生选择，固定到当前解答版本，不由模型默默更改。
- 每轮聚焦一个关键问题；提示从概念提醒、方法提示逐步到局部示范。
- 学生可以请求提示、跳步、查看完整答案或退出；不会无限追问。
- 保存每轮问题、回答、反馈、步骤、提示与动作，刷新后可继续。
- 退出或更换解答版本时，旧任务不得覆盖新会话状态。
- 默认答案此前已展示，过程属于辅导表现，不能被标为独立解题通过。

“先引导再揭晓答案”可以作为二期建议模式；只有学生主动进入该模式、且实际未暴露答案时，才能记录对应的帮助条件，不能靠修改模式名称抹除答案曝光记录。

### 4.4 个性化解析 P2-04

标准解答作为稳定基线；个性化版本记录对应学生、题目、标准解答版本、采用的教学依据和策略。

| 观察到的需要 | 解析调整示例 |
|---|---|
| 概念适用条件不清楚 | 先解释定义、条件与反例，再进入推导 |
| 运算容易出错 | 展开关键变形，标出符号、定义域和检验步骤 |
| 论证不完整 | 说明每一步为何成立，以及分类讨论为什么必要 |
| 学生希望简洁复习 | 保留关键思路与容易遗漏的检查点，允许展开完整步骤 |

个性化不能改变题目条件、正确答案或有效论证。新版本与标准答案冲突时不展示为合格解析；失败则保留标准解答并说明个性化生成状态。解释“为什么这样讲”时使用具体教学依据，不贴能力标签伤害学生。

### 4.5 费曼式教学验证 P2-05

定义：让学生用自己的话把关键概念或方法“教给助手”，通过追问暴露缺口，再让学生修正解释。助手验证的是解释质量，而不是复述长度或表达流畅程度。

流程：选择验证主题/关键步骤 → 学生先解释 → 按量规分析 → 针对缺口追问 → 学生修正 → 给出本次结果和下一步建议。

量规至少包括：概念准确性、推理连贯性、适用条件/边界、能否说明一个例子或反例。每项判断都要关联学生原话，明确不确定之处。

示例：学生解释分式不等式时说“分子分母都为正，所以分式为正”。助手追问“如果分子分母同时为负，结果如何？分母为零时呢？”；结果指出遗漏的情形，而非直接给出“已掌握”。

结果状态：本次解释达标、部分达标、仍需帮助、证据不足/待验证。记录解释次数、答案曝光、提示与示范，不自动折算成长期掌握分数。

- 不把“我懂了”、照抄标准解析或简单同意当作通过。
- 已看答案后的解释可以表明一定理解，但不能等同于未做过题的独立解决能力。
- 引用错解可以成为薄弱证据；正向证据只支持本次概念/解释表现，保留帮助条件。
- 二期用教师审核的概念追问量规/模板及当前题目开展验证，不必建设公共题库。
- 模型临时生成的示例只作讲解或观察，不能冒充已审核题库题，也不能单独证明新题迁移。
- 三期通过未做过的相似题，将解释表现与独立迁移表现分开验证。

### 4.6 二期边界

二期必须形成“信息 → 教学调整 → 学生作答/解释 → 有证据的反馈”闭环。OCR 修正、多题识别、延迟复习等是独立选做项，不以它们完成作为核心教学闭环上线的前提。公共题库、RAG 与相似题匹配仍属于三期。

## 5. 三期：数学题库、RAG 与相似题匹配

### 5.1 题库建设 P3-01

只使用项目方自有或已获授权的资料。原始资料导入 → 题目/选项/小问/答案解析关联 → 知识点、方法和难度标注 → 去重 → 教师审核 → 发布 → 建立索引。

以完整题目及其子结构作为主要检索单元，不把任意 PDF 段落当作可直接呈现的独立题。保存来源、授权状态、内容版本和审核状态，未发布或已下架内容不可被推荐。

学生上传题目不会自动进入公共题库。题库运营与学生个人题目权限分开。

### 5.2 相似题匹配 P3-02

从题目详情进入“找相似题”，可选择目的：

| 类型 | 匹配依据 | 适合用途 |
|---|---|---|
| 同类练习 | 知识点、数学结构与条件形式相近 | 熟悉当前方法 |
| 解法相似 | 核心策略相近，题面不一定相似 | 识别方法并迁移 |
| 补薄弱点 | 围绕相关前置知识/错因，难度合适 | 补齐当前卡点 |

先用主题、知识点、题型、难度及可用范围过滤，再结合关键词与向量召回、数学结构信息和重排；具体模型及索引选型通过题库样本评测决定。

学生画像仅用于有权限的个性化匹配；没有画像时仍可按题目匹配。支持优先未做过、同难度/降低难度等条件。

结果建议默认展示 3—5 道，提供题干、题型/难度、相似理由和来源；答案按查看/练习场景揭晓。相似理由必须与实际结构或方法相符，不把检索分数称为“掌握概率”。

匹配不足时如实展示较少结果或暂无合适题，不用临时生成的题补齐为“检索结果”。向量相近不能自动证明解法相同，需使用教师标注样本评测。

### 5.3 RAG 与索引边界 P3-03

题库保存权威内容，索引保存可重建的检索投影。向量索引并不要求必须引入 MongoDB；存储与检索引擎分别选型。

索引记录题目 ID、内容版本、发布状态和编码版本；更新、下架、删除可追踪。最终展示前再次校验题目是否可用及版本是否匹配，避免异步索引延迟暴露失效内容。

使用 RAG 生成相似理由或补充讲解时，引用真实检索题目及其审核内容。模型生成说明与题库原文分别标识，不修改题库审核答案。

### 5.4 三期建议扩展：独立迁移练习

优先增加“一道未做过的相似题”验证，而非立即建设完整考试系统：先不展示答案、记录独立作答和帮助使用，再核对结果并解释错误。复杂解答题不能可靠批改时标记待确认。

该功能若获确认，记录为独立练习结果；与原题复习、引导表现、费曼解释分开，形成更可靠的画像修正证据。完整随机测验和全题型自动批改需额外立项。

## 8. 质量验收与阶段门槛

### 8.1 一期

建立教师审核的内部评测集，覆盖支持范围内的主要主题、题型、难度，以及印刷题、手写公式/错解。内部评测集不等于公共题库产品。

以下为建议评审目标，需基线测试与教师共同确认，不是已达成指标：

- 最终答案正确率 ≥97%、解析与步骤审核通过率 ≥95%、知识点标注正确率 ≥95%。
- 同时报有效解答覆盖率和端到端合格解答比例；OCR 失败、生成失败和结构校验失败不能从提交总量中无声排除。
- 文本和拍照分别统计；有多个小问时，整题口径要求所有小问正确，另报小问口径。
- 原始内容、数据库回读、展示四项和版本引用一致；重复请求、失败重试、跨账号、同题合并、变式不合并和删除恢复等验收场景全部通过。
- 支持范围以外的图形依赖题、模糊/缺条件提醒、多题切分不计为已完成功能。

### 8.2 二期

- 个性化解析在数学正确性上不得低于标准解析的约定门槛；同题对比评估适合性与可理解性。
- 引导按所选步骤启动、每轮目标清晰、提示逐级推进，教师审核通过率建议 ≥90%。
- 费曼结论与量规、学生原文一致；重点统计错误判为“解释达标”的比例，建议教师认可精确率 ≥90%，另报覆盖率和待验证率。
- 自述、辅导、提示后解释与独立表现的来源区分准确；看过答案后的表现不能产生“新题独立通过”记录。
- 无证据不新增确定薄弱结论；修改/删除证据后画像可追溯重算。

### 8.3 三期

- 上线前确定首批主题、有效题量、难度覆盖和教师审核产能；没有覆盖不承诺全高中数学题库。
- 用教师标注的相似题集合分别评估同类、同解法和补薄弱点场景；先建立基线，再约定 Recall@K、Precision@K 或排序指标，不混用一种“相似度”代表全部质量。
- 返回题目真实存在、授权有效、已发布、版本有效；未发布、下架及私人题目不泄露。
- 筛选、冷启动、无匹配、题库更新/删除和索引延迟用例通过。
- 若启用独立迁移练习，另验收帮助记录、作答判定和画像修正规则，不借检索上线直接宣称教学效果已验证。

## 9. 建议增加的教师能力

以下均为产品建议，尚未替用户确定开发范围。

| 建议 | 学生价值 | 推荐阶段 | 取舍与依赖 |
|---|---|---|---|
| 解答纠错与教师复核反馈 | 学生能指出错误，推动质量闭环 | 一期 S | 先做简单反馈与后台处理，不承诺实时人工答疑 |
| 易错点/适用条件提醒 | 避免只记住答案 | 二期 S | 关联当前步骤与真实错因，不提前当作能力诊断 |
| 分层提示与渐隐帮助 | 帮学生逐步减少依赖 | 二期优先，已纳入引导设计 | 记录提示/示范，不直接换算长期掌握 |
| 费曼解释的反例追问 | 发现概念边界理解不足 | 二期优先，已纳入费曼设计 | 需教师审核量规，避免流畅复述假通过 |
| 延迟回顾/间隔复习 | 检查过一段时间是否还能解释 | 二期 S | 先用个人题目，标记原题复习，不依赖题库 |
| 一题多解与方法比较 | 帮学生理解方法选择 | 二期 S | 只展示经过质量校验的方法，避免增加难度失配 |
| 未见过相似题的一题验证 | 验证能否独立迁移 | 三期优先建议 | 依赖已审核题库，答案揭晓与帮助记录完整 |
| 图形交互、语音或具象数字人 | 拓展几何表达和交互方式 | 核心闭环稳定后单独评审 | 图形语义、语音数学识别与形象成本分别评估 |

优先建议是“分层提示＋费曼追问＋一道新题验证”，它们分别对应帮助理解、检查概念边界与检查迁移；形象与动画可以随后增强教师体验。

## 本次更新：独立记忆压缩存储（2026-10-27）

长期记忆暂不实现。本次仅处理会话历史摘要，不从摘要推断学生已掌握知识或长期能力。

- 三张基础表继续承载会话、原始问答和分支；`agent_memory_compact` 保存每次成功压缩的结构化内容，旧版本保留。`agent_conversation.ext.Summary` 只保存当前引用与覆盖元数据，不重复存正文。
- 解题与压缩均使用 `BAILIAN_CHAT_MODEL` 指定的同一百炼模型，服务启动后自动运行后台压缩。独立 Worker 也使用该变量，无需配置单独摘要模型。
- 默认应用上下文预算 16384、输出预留 4096，可用输入预算 12288；80% 向上取整为 9831。成功轮结束后优先采用供应商返回的完整请求输入 token 数（包含 SP、工具和上下文），没有供应商用量时使用保守估算，查询结果明确标注来源。
- 未覆盖历史超过 4 个完整问答轮次才有可压缩内容；保留最近 4 轮，压缩更早前缀。不是每 N 轮定期提取。摘要输出上限 2048 token，优先按供应商用量校验；无用量则用保守估算。
- 装配前的安全检查仍使用保守 UTF-8 字节估算，并非精确 tokenizer，因此可能在供应商真实输入达到 80% 之前触发强制压缩。当前请求不等待；返回可重试错误。只剩保留轮次或单轮过大时可能没有可压缩前缀，重试本身不能解决这类超限。
- 压缩模型调用在事务外；发布时在同一事务内新增压缩版本、校验分支/epoch/来源前缀/旧摘要 revision/任务租约并更新会话引用。过期结果不发布，失败按有界重试保留旧有效摘要。
- 压缩不更新或删除 `agent_message` 原始内容和哈希。下一轮仅以“摘要＋未覆盖完整问答”装配模型上下文。显式遗忘/删除是另一条数据清理流程。

### 验证接口

`GET /api/v1/conversations/{conversation_id}/messages?limit=100`

返回全部角色的存储消息，包含待回答输入和非当前分支；每页 1—100 条，通过 `next_cursor` 继续读取全部记录。学生身份由服务端绑定，不能通过参数访问其他学生。

| 字段 | 含义 |
|---|---|
| messages | 原始存储消息的 ID、角色、状态、分支、轮次、content.items、original_input、内容/前缀哈希、时间 |
| messages[].in_active_chain | 是否属于当前模型使用的分支链 |
| messages[].covered_by_current_compact | 是否被当前有效摘要覆盖；true 的原消息仍完整返回 |
| total_messages / next_cursor | 总消息数和后续页游标 |
| current_summary | 当前生效摘要、压缩 ID、revision、覆盖游标和模型 |
| recent_compacts / compact_versions | 最近 20 个压缩版本及全部版本数量；数据库保留全部版本 |
| last_model_usage | 最近成功轮模型输入/输出用量，source 区分 provider 与 estimate |
| policy / trigger_tokens | 当前默认配置与 9831 的触发阈值 |

分页期间消息集合、分支或摘要版本变化时返回 409，调用方重新从第一页读取，避免混合不同快照。原 `GET /api/v1/messages` 为输入记录列表，不用于验证完整对话。

### 部署与验收顺序

先显式运行 `go run ./cmd/runtime-db` 应用 004 迁移（003 基础表不变），再启动新版服务。已有会话内联摘要会迁移到独立表，原始消息不改；迁移可重复执行。不要让旧版写入端与新版压缩发布并行使用同一会话。

依次验证 80% 边界、结构化摘要及来源校验、两版摘要累计、原始消息内容/哈希不变、最近 4 轮上下文、完整消息分页、学生隔离，再验证真实百炼生成。强制压缩联调与 80% 自动触发测试分别记录，不把强制联调描述为真实用量达到阈值。


## 标识治理：自增主键与业务发号（2026-10-27）

四张表统一使用 `id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY` 作为内部行主键。`scope_key` 保留完整 `(namespace, subject_id, conversation_id)` 的隔离哈希语义，不改成自增数，不接受客户端直接传入。自增 id 只负责数据库行定位，不代替消息链位置、业务 ID、授权或幂等键。

| 字段 | 新数据规则 | 兼容规则 |
|---|---|---|
| id | 每张表独立自增；仅在该表内有意义，允许空洞 | 005 迁移为已有行补齐，后续迁移不重新编号 |
| conversation_id | 服务端 UUIDv7，`c_`＋32 位十六进制字符串，34 字符 | 已存在的会话号继续有效；普通消息接口不再按客户端自定义编号创建新会话 |
| branch_id | 服务端 UUIDv7，`b_`＋32 位十六进制字符串，34 字符 | 旧 ROOT 哈希/分支 UUID 不改写；已存在会话始终复用其实际当前分支 |
| turn_id | 接受新问题时发出 `t_`＋32 位 UUIDv7；幂等命中时直接复用 | 旧轮次号及其派生消息映射保持兼容 |
| message_id | 同一个服务端轮次号派生 `mu_`/`ma_` 两个消息 ID，35 字符 | 旧轮次沿用旧哈希映射，既有消息 ID、父引用和前缀哈希不改写 |
| client_request_id | 客户端请求幂等键，可继续使用 UUID；重试不更换 | 不与 message_id 或 conversation_id 混用 |
| compact_id | 本次不变，继续按压缩来源/版本生成内容关联哈希 | 独立的自增 id 不改变压缩版本和引用 |

统一发号实现为 `internal/platform/idgen`，复用当前依赖的 UUIDv7 实现，不引入新的发号表或外部服务。类型前缀方便识别；时间段有序，同进程同类型连续发号单调递增，多进程之间不保证严格全局顺序。业务时间查询使用 created_at，消息因果顺序使用 branch/position/parent_message_id，不能按业务 ID 代替。UUID 只是标识，不是权限凭证。

一轮成功问答仍只有两条物理消息。两条消息使用同一个已发出的轮次号，分别加 mu/ma 前缀，是为了在模型执行前预知身份，同时让重复提交、消息事件、展示投影和最终落库得到相同 ID。共享映射由 `state.MessageID` 实现；不在发送事件时重新随机发号。mu/ma 内的时间表示该轮的发号时间，并非助手完成时间。

### 创建与提交顺序

1. `POST /api/v1/conversations`，JSON 为 `{ "client_request_id": "本次创建会话的请求键" }`。返回服务端生成的 conversation_id、branch_id。
2. 创建请求的唯一约束为 `(namespace, subject_id, creation_request_id)`；同一学生重试复用同一会话。不同学生的相同请求键互不影响。会话和 ROOT 分支在一个事务提交。
3. 使用返回的 conversation_id 调用原有 `/api/v1/messages` 或 `/api/v1/agentic/chat`。未创建的会话返回 404，不能从消息入口绕过发号；已存在旧格式会话继续可用。
4. 消息使用原有 `(subject_scope, client_request_id)` 唯一约束幂等；命中时返回原 turn_id/message_id，不能重新发号。成功封口、SSE 投影与 TurnCompleted 事件统一引用同一套消息 ID。

网页新建对话先使用本地草稿标识，第一次发送前向服务端创建正式会话；草稿标识只用作会话创建的幂等请求键。丢失创建回执时重试仍取回同一正式会话。已有本地会话继续使用旧 ID，消息的本地 UI 标识与 client_request_id 不充当数据库 message_id。

### 迁移及实现顺序

先应用 003/004 基础迁移，再通过显式 `cmd/runtime-db` 应用 `005_identifiers.sql`。005 将原主键转换为唯一键，增加自增主键；保留 scope_key、消息/分支组合唯一约束、内容和哈希。MySQL DDL 不属于普通业务事务，逐表检查可重复执行；失败时修复后继续，不删除或重建旧数据。

落地顺序：自增主键迁移 → 统一发号器与旧号兼容映射 → 服务端会话创建及幂等 → 网页草稿转正式会话 → 消息/事件/分支联动 → 并发与迁移回归。迁移不重写任何历史业务 ID，不通过更新旧消息来统一外观。


## 本次细化：会话查询与题目保存验收

新增只读会话记录界面，从当前对话进入或按 conversation_id 查询，支持完整消息分页、角色/压缩覆盖筛选、搜索已加载内容、原始数据、历史摘要版本和最近模型输入用量。压缩前的用量会明确标记，不把摘要预览视为当前状态变更。

一期正式题目保存的验收粒度为：服务端题目 ID、文字原输入或图片 OCR 原始转录、图片路径与 OCR 结果路径、题目答案、题目解析、按顺序保存的解题步骤列表。图片与 OCR 路径各自可追溯；个人题目和 Agent Store 对话记录分别保存并建立来源关联。只有正式业务提交成功才显示“题目已保存”，单纯保存 query 或问答文本不满足该项验收。

当前只交付会话查询与接入设计；正式题目业务仍按《实现顺序》S1—S6 实现和验收。输入范围继续为高中数学清晰完整单题、文字教学助手，图片路径只用独立 OCR 识别、不依赖配图。二期个性化与三期 RAG 范围保持原定。


## v7.0 当前可用功能

学生在网页输入一道完整文字题，获得答案、解析、解题步骤和主题级知识点。原始输入先保存，解答通过结构校验和模型复核后自动正式收录。题目有服务端 question_id，每个步骤有稳定 step_id；页面刷新或从“我的题目”进入可以读取正式结果。

当前支持文字，图片与 OCR 仍不可上传；数据库预留路径为 NULL。解题失败保留原文并可使用相同请求重试，重复点击/重试不会产生同一任务的第二份结果。不同新请求的相同题目暂不自动合并。新建解答版本、教师人工审核界面、引导和反馈队列尚未开放，页面不伪造这些功能已完成。

## 解题 SSE 流式交付（2026-10-27）

网页使用 POST /api/v1/solve，提交原有JSON并设置 Accept: text/event-stream。未设置该Accept时保留原JSON响应，便于既有调用方兼容。请求格式/归属等前置错误仍以HTTP JSON返回；开始流后使用error和done事件表示失败。

事件：accepted（原始消息已保存）、progress（准备/识别/生成/校验/保存）、text_delta（模型公开文字增量）、draft_reset（开始新候选）、draft（答案/解析/步骤的待校验增量快照）、ocr（识别原文）、validation（是否通过及问题）、solution（数据库正式回执）、error、done。另每8秒发送heartbeat。event id只用于本连接顺序，不支持Last-Event-ID续传；断线后使用同一client_request_id重试，先读回执，已有结果不重跑模型或OCR。

主模型实际调用供应商Stream，边接收边投影，完整拼接schema.Message后再交给既有Eino ReAct同步Loop，所以四节点图和工具执行协议不变。只投影公开Content以及validate_solution候选中的answer/analysis/steps，不投影ReasoningContent、原始工具JSON、系统提示、密钥或独立复核器输出。每次生成受响应大小限制，增量草稿仅用于展示，不进入草稿校验/数据库保存逻辑；完整JSON仍须经既有严格校验及事务提交。

页面将流式内容标记为“待校验，尚未正式入库”，只有收到committed=true正式回执才显示已保存。校验修订会替换当前候选；失败保留原图、原始消息、OCR和公开反馈。OCR公式缺损应重传清晰完整题目或改用文字，不将重复解题视为重新OCR。

SSE写入带锁，防止心跳与模型分片交错；刷新失败取消执行；每次写入有15秒期限。请求预算与原185秒范围一致，客户端总等待210秒。流中断在提交前不生成正式题目，提交后仍以回执修复并幂等重放。
